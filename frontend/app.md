## User Roles

| Role | Description |
|------|-------------|
| `applicant` | Students who submit scholarship applications |
| `scorer` | Staff who score submitted applications |
| `app_admin` | Manages application lifecycle and settings |
| `school_admin` | Manages schools and counselor accounts |
| `counselor` | Views and supports their school's applicants |

## Features

### Scholarship Application
- Questions are fetched dynamically from the backend
- Supported question types:
  - **Short answer** — single-line text input
  - **Long answer** — multi-line textarea
  - **Multiple choice** — checkbox group (many selections)
  - **Single choice** — radio group (one selection)
  - **File upload** — upload separately via multipart form; store returned file reference ID in the JSON payload (do not embed file content in JSON)
- Applications can be saved as draft and submitted when complete
- Applicants can view their submission status

### Application Scoring
- Scorers see a queue of submitted applications assigned to them
- Each application can be scored section-by-section or holistically
- Scores and comments are saved per reviewer
- Aggregate scores visible to `app_admin`

### Application Administration
- View all applications with filtering, sorting, and pagination (DataTables)
- Change application status (draft → submitted → under review → awarded / rejected)
- Assign applications to scorers
- Export application data
- Manage scholarship cycles / deadlines

### School Administration
- CRUD for school records
- Invite and manage counselor accounts per school
- View applicants by school

### Reference Document Upload
- Students are issued a unique reference code per application (generated by the backend)
- Students share their code with a reference (teacher, counselor, employer, etc.)
- References visit a **public, unauthenticated page** and enter the code to access an upload form
- Accepted file types: `.doc`, `.docx`, `.pdf`
- File is uploaded via multipart form; the backend associates it with the application via the reference code
- Students can see the status of each expected reference on their dashboard (pending / received)
- Reference codes are single-use and expire after the application deadline

### Counselor Dashboard
- View applicants from their school
- Track application status per student
- Send nudges / reminders (via backend)

## Routing (`src/router/index.js`)

```
/login                          → LoginPage          (AuthLayout, public)
/register                       → RegisterPage        (AuthLayout, public)

/dashboard                      → DashboardPage       (applicant)
/application/:id                → ApplicationFormPage (applicant)
/application/:id/status         → ApplicationStatusPage (applicant)

/scoring                        → ScoringQueuePage    (scorer)
/scoring/:applicationId         → ScoringDetailPage   (scorer)

/admin/applications             → ApplicationsListPage (app_admin)
/admin/applications/:id         → ApplicationDetailPage (app_admin)
/admin/settings                 → SettingsPage         (app_admin)

/schools                        → SchoolsListPage      (school_admin)
/schools/:id                    → SchoolDetailPage     (school_admin)

/counselor                      → CounselorDashboardPage (counselor)

/reference                      → ReferenceUploadPage    (public, no auth)
```

Navigation guards redirect unauthenticated users to `/login` and unauthorized roles to a 403 page.

## Pinia Stores

### `auth.js`
```js
state: { user, token, role }
actions: login(), logout(), fetchCurrentUser()
```

### `application.js`
```js
state: { questions, answers, currentApplication, status }
actions: fetchQuestions(), saveAnswer(), saveDraft(), submitApplication(), uploadFile()
```
> File uploads call a dedicated endpoint and store the returned `fileId` in `answers` — never embed binary data in the answers payload.

### `scoring.js`
```js
state: { queue, currentApplication, scores }
actions: fetchQueue(), fetchApplication(), submitScore()
```

### `admin.js`
```js
state: { applications, filters, pagination }
actions: fetchApplications(), updateStatus(), assignScorer(), exportData()
```

## Setup

```bash
npm create vite@latest scholarship-frontend -- --template vue
cd scholarship-frontend
npm install

# Core dependencies
npm install vue-router@4 pinia axios

# Tailwind
npm install -D tailwindcss postcss autoprefixer
npx tailwindcss init -p

# Icons
npm install @mdi/font

# DataTables (jQuery-free build)
npm install datatables.net-vue3 datatables.net-dt
```

### `tailwind.config.js`
```js
export default {
  content: ['./index.html', './src/**/*.{vue,js}'],
  theme: { extend: {} },
  plugins: [],
}
```

### `src/assets/main.css`
```css
@tailwind base;
@tailwind components;
@tailwind utilities;
```

### `src/main.js`
```js
import { createApp } from 'vue'
import { createPinia } from 'pinia'
import router from './router'
import App from './App.vue'
import '@mdi/font/css/materialdesignicons.css'
import './assets/main.css'

createApp(App).use(createPinia()).use(router).mount('#app')
```

## Notes

- All API calls go through `src/services/api.js` (Axios). The auth store attaches the Bearer token via a request interceptor.
- File uploads use `multipart/form-data` to a dedicated endpoint; the JSON application payload references the returned file ID.
- DataTables is wrapped in `DataTable.vue` to keep jQuery / DataTables lifecycle concerns isolated from Vue's reactivity.
- Role-based access is enforced both in Vue Router guards and visually (hide nav items the role cannot access).
